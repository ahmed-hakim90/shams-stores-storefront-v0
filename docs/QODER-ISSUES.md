# سجل المشاكل والمتبقي لـ Qoder

آخر تحديث: 19 سبتمبر 2026. الأولويات لترتيب العمل وليست تصريحًا بأي تغيير إنتاج.

## P0 — رحلة الدفع غير مثبتة بالكامل

**الدليل:** ظهرت الطرق في الإنتاج ثم تجربة المالك رُفضت بـ `Invalid parameter(s): shipping_lines`. السبب المحدد أُصلح ونُشر: `instance_id` كان number ويجب string وفق REST schema الحي.

**المتبقي:** تأكيد إنشاء/تسعير Woo، تحميل Pixel، البطاقة والتقسيط، احترام callback overrides، ومطابقة مبلغ/عملة/تكامل الطلب. لا تضغط Pay/Place order تلقائيًا على سلة المالك. استخدم staging ومفاتيح Test متوافقة؛ لم نجد تكامل تقسيط sandbox مستقلًا مثبتًا بالحساب.

**معيار الإغلاق:** نجاح وفشل وإلغاء، coupon/shipping/variation، HMAC صحيح/خاطئ، callback مكرر ومبكر ومتأخر، وعدم اعتبار pending/authorization/refund/void دفعًا ناجحًا.

## P0 — قفل محاولة الدفع القديمة بعد الرفض

**الحل المطبق في الكود (19 سبتمبر 2026، بانتظار نشر مصرح):** أي فشل بعد إنشاء الطلب وفي مراحل تجهيز الدفع (`create_intention`/`validate_intention`/`save_intention`/`complete_claim`) ينفذ `completeClaim` معوّض داخل الـ catch، فيرتبط الـ claim بالطلب ويتحول من `running` إلى `complete` قابل للاستئناف؛ الـ mutex الذري `running` يبقى فعالًا طوال التجهيز نفسه فلا ينشأ intention موازٍ. مسار الـ resume يعيد التجهيز على **نفس الطلب** فقط (سر مخزن صالح، أو إعادة تجهيز بحدود: cooldown ‏20 ثانية عبر `_paymob_prep`، سقف 5 محاولات، وdedupe داخل الـ worker). الجلسة العالقة بـ `payment_session_busy` تُفك عبر كوكي الملكية `shams-order` بعد التحقق من `order_key` وحالة الطلب؛ بدون الكوكي أو مع عدم تطابقه تبقى fail-closed. لا تغيير في إضافة الووردبريس ولا release لأي claim. الاختبارات: `tests/paymob-deployment.test.mjs` (تعويض، resume، cooldown، سقف، busy بالكوكي وبدونه).

**السبب التاريخي:** intention route ينفذ paymentClaim قبل createPendingOrder. schema rejection قبل إنشاء الطلب لا يحرر claim، والبلاجن يمنع release لcheckout. المحاولة قد تظهر لاحقًا 409 busy/changed بدل خطأ الشحن.

**أماكن المراجعة:** `app/api/payments/intention/route.ts`، `lib/payments/session.ts`، `wordpress-plugin/shams-headless/includes/class-payment-sessions.php`، `tests/headless-payment-sessions.php`.

**المتبقي يدوي/تشغيلي فقط:**
1. hard-kill للـ worker قبل الـ catch (claim يبقى `running` بلا ربط بطلب) — معالجة تشغيلية مصرحة، لا مسح تلقائي.
2. تغيّر الـ fingerprint بعد reload (سلة/عنوان/طريقة مختلفة) → `payment_session_changed` يفشل مغلقًا بالتصميم؛ الاستئناف يتطلب نفس البصمة.
3. الطلبات العالقة قبل هذا الحل (30309/30310/30311): إلغاؤها من Woo admin قرار المالك للتسويات فقط؛ مسح خيارات `shams_payment_*` من الووردبريس يحتاج تصريحًا صريحًا ولا يُنفذ تلقائيًا.

**ما لم يحدث:** لم نقرأ أو نمسح claim الخاص بالمالك، ولم نثبت غياب أي طلب/Intention من محاولات أخرى. إصلاح string لا يعالج القفل القديم.

**خطوات المعالجة:**
1. راجع Woo وPaymob والـ logs بالتوقيت نفسه دون نشر بيانات العميل أو مفاتيح الطلب. اربط claim بالسلة في بيئة محمية؛ لا تطلب من المالك إرسال cookies في الشات.
2. ميّز رفض schema المؤكد قبل الكتابة عن timeout/5xx أو استجابة ناقصة بعد احتمال الكتابة.
3. لا تمسح كل shams_payment_*، ولا تغيّر cart cookie لتجاوز الحماية، ولا ترجع order إلى paid يدويًا.
4. صمّم تعافيًا محددًا للحالة التي ثبت أنها لم تنشئ طلبًا، بصلاحية ضيقة وملكية claim وتحقق ذري من الحالة. احتفظ بالقفل عند أي نتيجة غير مؤكدة.
5. لا تعتبر TTL تلقائي أو زر Try again علاجًا: العامل الأول قد يكون كتب الطلب فعلًا. زر «Complete payment for Order #X» ليس Try again عام: يستأنف نفس الطلب المثبت رقمه ولا ينشئ طلبًا جديدًا أبدًا.

**معيار الإغلاق:** اختبار التزامن وفقد الرد ورفض schema، وإعادة المحاولة لا تنشئ طلبين، ومعالجة claim القديم بقرار تشغيلي موثق ومصرح.

## P1 — حسابات التحويل لا تصل للإنتاج بعد

الواجهة ومسار Next منشوران، لكن آخر GET bank-transfer أعاد null. Commerce UX 0.8.3 غير مثبت بواسطة الوكيل. راجع ZIP والدليل ثم افحص site-content.bank_transfer. قارن الحسابات مع إعدادات Woo الفعلية؛ لا تضعها في env كنسخة منافسة. تأكد أن البيانات المعدّة للنشر هي تفاصيل الاستلام التجارية المعتمدة.

معيار الإغلاق: اختيار bacs يعرض الحساب/البنك/المستفيد وCopy، يحافظ على leading zeros، رفض Clipboard له fallback، ويختفي المصدر عند تعطيل BACS. لا تدّعِ أن النسخ يؤكد التحويل. راجع صفحة نجاح BACS وتعليمات ما بعد الطلب أيضًا؛ هذا التغيير يستهدف checkout فقط.

## P1 — الضمان والوكيل يحتاجان تحديث المصدر

الواجهة منشورة وتستهلك custom_label؛ Commerce UX 0.8.3 يحتويها. اختبارات الحقول السابقة على Canon R50 و12 منتجًا رجعت flags=false وwarranty_text فارغًا، لكن الاستجابة القديمة لم تميز النص الخاص من الافتراضي. لا تستنتج من هذا أن كل الكتالوج بلا ضمان.

معيار الإغلاق: نص خاص مع checkbox off يظهر بالكارت/المنتج/quick search/search page، الفارغ لا يُظهر default غير مفعّل، enabled legacy يبقى متوافقًا. تحقق cache revalidation (product content 120 ثانية وقد تُخدم نسخة stale أثناء التحديث)، ولا تطهر كاش الإنتاج بلا حاجة وتصريح.

## P1 — حاسبة التقسيط غير منفذة

لا توجد بيانات مثبتة للبنوك/المدد/الرسوم أو حساب قسط المنتج. يوجد installment notice واختيار بوابة فقط. نحتاج مصدر خطط رسمي أو سياسة تجارية معتمدة، ثم تعريف احتساب مقدم/فائدة/رسوم وحدود الأهلية والعملات. لا تستخدم أسعار تقديرية على أنها عروض فعلية.

## P1 — توافق فورم الدفع مع إعدادات WordPress جزئي

requiredCheckoutFields محلية، وليست schema مستوردة من WordPress. الهاتف 01 + 9 أرقام محليًا؛ Paymob يتطلب اسم العائلة والبريد. المطلوب النهائي اعتماد إعدادات WordPress مع قرار الهاتف الإجباري. يجب تحديد owner/API آمن قبل توحيد الحقول؛ لا تُعد تدخل Commerce UX بفورم WordPress.

## P2 — استعادة الجلسات وتجديد السلة

claims لا تنتهي تلقائيًا، وexpired intention أو تغير السلة أثناء الدفع يحتاجان تشغيلًا مراقبًا. webhook mutex قد يعلق عند انقطاع worker. نجاح الطلب ينظف السلة فقط إذا snapshot يطابقها. اختبر بقاء تعديلات تبويب آخر، ومصادقة ملكية الإيصال؛ لا تمسح بيانات عند الشك.

## P2 — بطء المصدر وتجربة الأخطاء

لوحظ تأخير Woo/اختفاء تنويه عند timeout ثم ظهوره بطلب لاحق؛ لا توجد مقارنة أداء إنتاج موثقة. المحتوى اختياري بمهلة 8 ثوانٍ، طرق الدفع المصدرية أبطأ أحيانًا. قس العدد والزمن وأسباب الفشل؛ لا تعالج المشكلة بعرض طرق أو أسعار stale دون فحص صلاحيتها عند الدفع. راجع رسائل upstream الخام الظاهرة للعميل والتفرقة بين validation ومشكلة تكامل.

## P2 — بقية المشروع

العربية الكاملة/RTL ومبدل اللغة، schema checkout، الأداء المقاس، بعض commerce_ui/hotspots، واختبار الحساب والمفضلة نهاية لنهاية ما زالوا ضمن backlog. لا تفترض اكتمالهم من وجود endpoint. HeroCarousel المحلي هو مالك الهيرو الحالي؛ لا تعِد تشغيل ManagedHero تلقائيًا.

## مشاكل أُصلحت وليست عملًا مفتوحًا

- Headless 1.2.0 fatal: تكرار Shams_Auth::register؛ 1.2.1 يغير customer handler إلى register_customer. لا تثبّت 1.2.0.
- PHP-WASM قد يرجع exit 0 بعد fatal؛ check-headless.py يفحص success markers أيضًا.
- الإنتاج كان checkout/paymob=false؛ صار true بتصريح المالك، وظهر الأربع طرق.
- shipping_lines.instance_id صار string مع اختبار boundary. لا تُعد تغييره إلى رقم بناءً على Store API.

راجع [الحالة المعتمدة](QODER-HANDOFF-2026-09-19.md) قبل تغيير أي بند إلى «تم».


## حادثة متابعة — محاولتا 19 سبتمبر بعد النشر
قراءة Woo فقط وجدت طلبين headless 30309 و30310 pending، بلا _paymob_intention_id محفوظ. سجلات الإنتاج وقت 15:39 و15:42 Cairo من deployment dpl_H83mz8JgZoeHmPBreFYbE8EFGEtC أعادت SERVER_ERROR/502 دون مرحلة. هذا deployment أحدث من تسليم الوكيل السابق؛ HEAD المحلي صار 4d9c744. لا يمكن إثبات غياب Intention لدى Paymob من غياب metadata وحده. لم تُلغَ الطلبات أو تُحرر claims.

تعديل المتابعة: grid عمود واحد/عمودين لطرق الدفع؛ PAYMENT_REVIEW_REQUIRED للأخطاء بعد امتلاك claim، ومنع تغيير الطريقة أثناء حالة غير مؤكدة، وسجل آمن لمرحلة تجهيز الدفع دون بيانات العميل. هذه تحسينات أمان وتشخيص وليست إثبات إصلاح سبب توقف Paymob. مراجعة الطلبين وربط Paymob ما زالا مطلوبين.

تعديل 19 سبتمبر (لاحق للحادثة): تحليل متسامح لاستجابة Intention (`id` رقمي، `intention_order_id` نص رقمي، `payment_methods` بأشكال مختلفة مع fallback لأسماء الطريقة من نوع الخيار)، وسجلان تشخيصيان بدون بيانات عميل: `[paymob-reject]` (حالة الرفض ورسالة Paymob فقط) و`[paymob-intention-shape]` (أسماء مفاتيح الاستجابة فقط)، ومسار استئناف كامل موثق في قسم القفل أعلاه. السبب الجذري لتوقف Paymob يبقى **غير مثبت** حتى نجاح محاولة حية؛ عند أول محاولة راقب في Vercel: `[paymob-reject]` ثم `[paymob-intention-shape]` ثم `[payment-preparation]` بالمرحلة. لو ظهر رفض 400 بسبب شكل حقل (مثل صيغة الهاتف) يُصلح الـ payload بسطر واحد موجّه بالسجل.
